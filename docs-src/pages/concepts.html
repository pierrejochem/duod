How duod works

duod runs every service in two slots, blue and green. One slot serves traffic. The other holds the next version until it is healthy.

Core concepts

App
One independently deployed service. It has its own Git folder (source.path), its own Compose projects, its own state and its own Traefik file.
Slot
One color of an app. duod runs the same compose file twice, as the projects <app>-blue and <app>-green.
Active, preview, previous
The active slot serves public traffic. The preview slot holds the new version under test. The previous slot is the stopped old version kept for rollback.
Route
One compose service published through Traefik. An app can have several routes that switch together.

Rollout lifecycle

  1. Detect. A webhook or poll fetches Git and resolves the newest commit that touched source.path.
  2. Preview. The commit is extracted into the idle slot's own directory, so each slot has an immutable checkout of its revision. Whatever still runs in that slot is removed, then docker compose up -d starts the new version as project <app>-<color>.
  3. Wiring check. Every routed container (<app>-<color>-<service>-<n>) must exist and be attached to duod-edge. A missing networks: entry fails immediately with a clear message, not with a health-check timeout.
  4. Pre-promotion analysis. duod adds probe routers for the new slot on Traefik's private duod entrypoint and checks healthCheck.path through Traefik. That is the same network path real traffic takes. With revisionHeader, the app must also echo the new commit SHA.
  5. Paused or promoted. The rollout waits for duod promote, or for autoPromotionSeconds. With autoPromotionEnabled it promotes at once.
  6. Switch. The app's Traefik file is rewritten atomically. Every generated file carries a generation hash that Traefik returns in X-Duod-Generation. duod waits until Traefik serves the new generation before it reports the promotion. If Traefik does not load it within confirmTimeout, the old file is put back. Open connections to the old slot finish normally.
  7. Post-promotion analysis (optional). The public URL is watched. On failure duod switches back automatically.
  8. Scale down. After scaleDownDelay the old slot is stopped but kept, so duod rollback only has to restart it, health-check it and switch.

Phases and sync status

duod list shows a phase and a sync status per app, like Argo CD. Synced means the Git target revision equals the active revision. OutOfSync means they differ. Healthy means the active slot serves the target. Degraded means the newest revision failed and the previous one still serves. Paused means a healthy preview waits for promotion.

Failed revisions

A failed or aborted revision is recorded in failedRevision and is not retried on every tick. Push a fix (a new commit) or run duod retry <app>. A new commit that arrives while a rollout is paused replaces the preview.

Parallel, independent rollouts

  • One app per service. A failing rollout of api never blocks, delays or rolls back shop.
  • Concurrent rollouts. Every app runs its own reconcile loop, so a push that changes three services rolls all three out at the same time. maxConcurrentRollouts caps how many deploy at once. The others are queued with a RolloutQueued event.
  • Monorepo-aware. An app's target revision is the newest commit that touched its source.path.
  • Coupled services. Services that must switch together, such as a frontend and its BFF, can be several routes of one app. They share one Traefik file and change color in a single atomic write.

Self-heal and state

With selfHeal (on by default) duod restarts the active slot and reverts manual edits of the proxy config. State is stored in /var/lib/duod/state/<app>.json and survives restarts. If duod dies in the middle of an analysis, the rollout is redone. A paused preview stays paused.

Code layout

cmd/duod             CLI + operator entry point
internal/controller  per-app reconcile loops, blue/green state machine, rollout limiter
internal/proxy       traffic-switch interface
internal/traefik     dynamic file per app, probe routers, generation confirm, network check
internal/apache      include file, configtest, graceful reload
internal/gitsrc      git mirror, path-scoped revision, per-slot checkout
internal/compose     docker compose per slot
internal/health      pre/post-promotion analysis
internal/api         REST, webhooks, metrics
internal/state       persisted state
